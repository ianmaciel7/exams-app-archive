# Design foundations and state transitions

Canonical decision guide: https://github.com/ianmaciel7/exams-app-archive/blob/main/docs/references/ui-ux-research-sources/design-foundations-and-state-transitions-2026-11-25.md
Structured cross-index: https://github.com/ianmaciel7/exams-app-archive/blob/main/docs/references/ui-ux-research-sources/design-foundations-and-state-transitions-2026-11-25.json

- Start from user task, object, frequency, risk, platform and context, not aesthetics. Compare alternatives; distinguish standards, guidance, heuristics, trends and hypotheses. Research additional primary sources and record limitations; #103–#105 track deeper validation, #102 coverage, #94 benchmark integrity.
- Color: choose visual direction, neutral surfaces, accent, semantic roles and tonal ramps. Use primitive → semantic → component/state tokens. OKLCH is approximately perceptual; check gamut, alpha/composition, theme and browser support. WCAG 2.2 AA requires 4.5:1 for normal text, 3:1 for large text and applicable non-text contrast; never use color alone. 60/30/10 is optional. Categorical/sequential/diverging palettes depend on data semantics. APCA/WCAG 3 drafts do not replace WCAG 2.2.
- Motion: choose intent (feedback, reveal, spatial continuity, progress, direct manipulation or emphasis) before technique. Distinguish productive/expressive, tween/spring, origin-aware transitions, entry/exit, easing, duration, distance, frequency, interruption, reversal and reduced motion. Do not impose universal milliseconds or delay feedback/focus until animation ends. Test rapid input, cancellation and frame cost.
- Focus: distinguish visual attention, keyboard focus, selected, active and focus mode. Use scale, contrast, grouping, spacing and typography; minimize competing emphasis. Preserve logical keyboard order, visible non-obscured focus, modal focus management and restoration; avoid stealing focus during async updates.
- Screen composition: task analysis → information architecture → flows → sketch/wireframe → visual direction → states/motion → prototype → test/iterate. Choose single-column, list-detail, supporting pane, tabbed workspace, split, dashboard, feed or canvas by simultaneous information needs; no mandatory three panels, cards or borders. Validate reflow, density, typography, iconography, alignment, spacing, container/viewport, keyboard/touch and scroll continuity.
- State modeling: separate variant, state, event, guard, effect and visual animation. Interaction states (default, hover, focus-visible, pressed, selected, checked, expanded, disabled, invalid, drag) may combine; define precedence. Data/operation states (initial loading, refreshing, empty, partial, stale, pending, optimistic, success, error, timeout, retry, offline, conflict, cancel, rollback, streaming) require real semantics and preserved context.
- Transition contract: component, from, event, guard, to, side effect, focus, announcement, visual feedback, motion, duration/easing only if verified, interruption/reversal, fallback, evidence and tests. Use statecharts where complexity merits; avoid unnecessary libraries. Visual techniques include fade, slide, morph, expand/collapse, reorder, shared element, enter/exit, stagger, FLIP and view transitions. Validate support, reduced-motion, forbidden paths, races, repeated events, retry and rollback. A screenshot cannot prove motion. Example (proposed): selected → submitting → correct/incorrect/error; retry/cancel explicit; result independent of animation.
- Evidence and validation: use WCAG 2.2, ARIA APG, CSS Color, DTCG, Radix, Material, Apple, Carbon, Atlassian, NN/g, GOV.UK, SCXML, CSS/MDN transitions and Motion; revalidate candidate sources and version-specific claims. Distinguish observed, documented, tested and proposed. Combine general guidance and original historical evidence through shared-ux-knowledge; no private data publication, no circular delegation, no synthetic results counted as real validation. Keep existing catalogs intact.
