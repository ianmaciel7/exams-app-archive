## Design decision gates

- Content first: establish what the user reads or operates; keep navigation and controls recognizable but subordinate. Liquid Glass is a native Apple functional layer for navigation and controls above content, not blanket glassmorphism on cards, radio rows, question text or canvas. In web UI start with opaque, readable surfaces; justify any translucent floating material by spatial context and verify actual composited contrast, fallback and scroll behavior.
- Hierarchy and alignment: semantic type roles, optical alignment and deliberate indentation; distinguish heading, question text, answer, metadata and action; text can wrap and row height grows. Adapt by available width, zoom, text scale and input capabilities rather than user-agent sniffing. Preserve task order and accessible focus; do not simulate native chrome.
- Geometry: use consistent shape families and nested/concentric corners only where rounded containment needs them; flush adjoining panes stay square if required. Avoid universal radius or shadow prescriptions. Map primitive to semantic to component tokens; define opaque fallback, elevations, functional seams and focus layers. Test light/dark and higher-contrast or reduced-transparency preferences where supported; do not claim native appearance from a CSS blur.
- Motion: state and relationship first, visual effect second. Preserve continuity on reversals and rapid repeated input; pointer-driven manipulation follows the pointer, release and cancellation resolve predictably; reduced motion keeps meaning and functionality. Do not add haptics, bounce, gradients or celebrations without task need. Separate application state from visual interpolation; no delay to answer feedback or keyboard focus. Treat motion as unverified until exercised, not proven by a static mockup.
- Feedback: route by severity and consequence. Quiet inline pending/success or answer result near the action; actionable error and retry preserve choice. Reserve disruptive alerts for justified high-risk interruptions. Show selected versus submitted versus locked as distinct semantics, correct/incorrect with labels and shape, technical failure separate from wrong answer. Avoid duplicated progress indicators, fake statistics and invented UI.
- Native versus web: prefer platform components and semantic Dynamic Type on Apple OS; web uses semantic HTML, native radio/button behavior, browser zoom and reflow, appropriate CSS units and target-size requirements from WCAG. Apple-specific target points, system colors, fonts and SF Symbols are not universal web tokens. Never redistribute proprietary fonts or symbols without license. Use licensed icons; verify Apple APIs against the actual OS/SDK if building native. Accessibility remains an independent acceptance gate, not a style claim.

## Operational visual and behavior review

1. Retrieve exact source, approved content, existing states, theme and viewport; label new directions as exploratory. Apply anti-ai-slop-design or equivalent review; a polished screenshot is not a working demo. Never invent an inspector, scoring, subscriptions, filters or routes to fill space.
2. Produce a material map (content, navigation, floating controls, overlays), shape/radius hierarchy, role/state token table, optical type/spacing rhythm and behavior/feedback matrix. Distinct full-system options require differences in these foundations, not just hue. Compare identical task content and states across variants.
3. Inspect actual readable renders in both themes and representative desktop/mobile widths; inspect long labels, text enlargement to 200%, browser reflow, keyboard focus, touch and contrast on actual adjacent/composited surfaces. Verify material fallback, active/pressed/selected/disabled/pending/error/retry, gesture cancellation/reversal, reduced motion and scroll/focus retention as applicable. Record evidence, unavailable tests and exceptions separately. Reject screenshot-like fake apps and raw tags presented as an interactive preview; if host cannot render, provide verified captures with honest limitations.
4. For the current exam-reading workspace, keep the actual competition list and question text central, preserve cardless reading and square flush seam, retain Answer beneath options, pagination after last question, safe retry and mobile drawer. Any new style is a separate exploration until owner approval. No automatic stage advance or palette replacement.
