# Fidelity non-regression gate

Fidelity is not coverage. A new stage may use fewer representative screens, but must not silently remove previously approved requirements. Read the immutable approved baseline, inventory, flows and decisions before generating a new artifact.

1. Derive a coverage ledger: stable requirement/state ID, predecessor SHA/evidence, current screen/component specimen and element IDs, status represented/missing/deferred, reason and review evidence. Use explicit owner approval for changed product behavior. A justified later-stage deferral must identify its target and source; an absent applicable visual state is missing, not deferred.
2. Complete representative screens: actual content and alternatives, all necessary actions, navigation, pagination, feedback and continuity. Distinguish intentional scroll viewport clipping from missing source. Reuse shared source for repeated components and overlay underlay. Cover applicable loading, empty, error, retry, pending, selected, correct/incorrect/locked, hover/focus/pressed/disabled, long content, narrow/phone and localized states using complete screens or focused component studies.
3. Inspect actual native captures at useful zoom in both relevant themes and device widths; compare against the immutable predecessor. A green build, valid element count, link to prior board or smaller scenario count does not establish visual coverage.
4. Record missing coverage and proactively notify the owner before presenting the artifact as ready. Allow explicitly labeled work in progress; block approval and progression until applicable gaps and visual review are resolved. Do not duplicate every historical artboard or implement out-of-stage functionality just to meet a count.
5. For Exam App verify dev at start/end, preserve approved boards, consult AGENTS.md and canonical release coverage ledger, and validate CI separately from human visual review.

Case 2026-11-27: approved Mid-Fidelity (21 states) to High-Fidelity (four initial specimens) at exams-app commit 2cc13ec. Published images exposed incomplete question alternatives/actions, missing pagination, lifecycle/feedback/control specimens, long-text and responsive detail, and inconsistent drawer underlay. Record the regression rather than call a green CI approval. The rule is a project quality convention, not a claim of universal UX law. Canonical record: https://github.com/ianmaciel7/exams-app-archive/blob/main/docs/references/ui-ux-research-sources/ux-design-activities-2026-11-25.md
## Rendered visual QA gate — 2026-11-27

Before publishing or asking for review, perform an actual rendered-layout audit of every affected specimen at readable zoom, in all relevant board themes and critical widths. For a High-Fidelity Wireframe, require explicit structural measurements, type hierarchy, component anatomy, state behavior, overflow/responsive rules and accessibility intent; distinguish proposals and native renderer presets from production tokens. Maintain a separate annotated specimen; do not add measurement marks to normal UI screens.

- Derive measurement endpoints and label text from the same geometry source as the component. A dimension is the measured distance, not a guessed caption. Give each label its own reserved annotation lane; keep title, notes, measurement labels, ticks, leaders, component text and controls clear of each other. Allow intentional overlays (drawer, selection, focus ring) only with a documented semantic reason. Do not treat every intersecting background rectangle as a defect.
- Inspect actual renderer bounds (including text wrap, font metrics, stroke width and minimum native shape size), not only source coordinates. A native 1-unit rectangle may render as a much thicker shape; use a supported line/stroke primitive or verified narrow vector if necessary. Verify thin redlines, tick endpoints, label contrast and optical alignment. Separate titles and labels by a measured clearance; move the annotation or expand its reserved region, never shrink type simply to hide a collision.
- Add automated checks where available: use stable element IDs and rendered bounding boxes, measure text or DOM Range rectangles after fonts and paint settle, assert required text-to-text / text-to-control clearances and containment, compare dimension labels to endpoint distances, and explicitly allow semantic overlays. Test normal, narrow, long-content and localized states. Use a negative fixture reproducing the actual overlap and a corrected positive fixture; a source-only check is not proof of rendered QA. If the renderer cannot expose geometry, inspect the genuine captures manually and record the limit.
- Capture each section independently, both themes, with manifest SHA and intended region; verify the region is fully visible and readable, no clipped tiles, toolbar occlusion or adjacent section mistaken for the target. Inspect the full-resolution image or zoomed crops, not just a thumbnail montage. Make capture evidence downloadable as soon as it is verified, independently of a slow optional portal build where workflow permits; do not claim a capture is accessible until it actually is. Show real captures inline in chat where supported.
- Keep a per-specimen visual QA ledger (SHA, theme, viewport, checked regions, issues, severity, result, evidence path). Fix every unexpected overlap, truncation, misalignment or missing required annotation, regenerate and recheck the affected states and their shared components before requesting approval. A successful structural CI or public deploy is not a visual QA pass. If validation cannot be completed, label the board as work in progress, identify the exact defect and block stage closure. Do not rely on the owner to find the defect first.

Regression case: Exam App High-Fidelity commit ea87642d5429ac79b6f2500277575fc9f8cb6c0a, workflow 46030571970, section 11 (Component Anatomy) showed the 112-unit width annotation overlapping the “Answer / Retry / radio / navigation” heading even though native element coverage and Playground validation passed. Section 10 also showed heavy redline strokes caused by native shape rendering. Record this as project evidence, not a universal design standard. Related earlier errors: stem/first-option collision in narrow answer feedback, lost approved states when increasing fidelity, inconsistent active documentation, and missing compositor tiles. The acceptance criterion is corrected real rendered evidence, not the addition of a checklist alone.
