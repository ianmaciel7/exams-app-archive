# Runtime UI verification — operational supplement (2026-11-28)

Use with the existing fidelity-non-regression, apple-hig-design-craft, audit and motion skills. Do not advance a design stage or certify accessibility on a partial test. [Canonical gap audit](https://github.com/ianmaciel7/exams-app-archive/blob/main/docs/references/ui-ux-research-sources/apple-skills-gap-audit-2026-11-28.md).

## V1 — evidence identity and runtime checks
Record commit/ref, actual build or deploy ID/hash, route, fixture ID, browser/device, viewport, theme, locale, zoom, input and test environment. Verify loaded app corresponds to the intended revision and fixture, not only a successful build or HTTP response. For every changed state, capture readable screenshot plus DOM/semantic accessibility snapshot, assert actual behavior using roles/labels and state, and record relevant logs/errors. Use coordinates only when semantic targets unavailable and justify. A successful screenshot proves rendering at that instant; keyboard, touch, network recovery and persistence require independent exercises. Run initial, loading, empty, error/retry, selected, committed, disabled and cancellation/reversal states as applicable. Use reproducible fixtures without private data; no fake screenshots or placeholder app. If runtime unavailable, label inspection-only and list exact unexecuted checks.

## V2 — accessibility and design craft
Combine automated checks with manual keyboard order, visible focus and restore, meaningful names/roles/values, screen-reader announcements and meaningful alternatives, zoom/reflow and text enlargement, contrast of composited surfaces, light/dark/high-contrast or forced colors, reduced motion/transparency where supported, touch/pointer and non-drag operation. Record tested assistive technology, version and scenarios; don't infer access from CSS or screenshot. Use applicable WCAG requirements, not imported Apple pt thresholds. For visual QA inspect real content, optical alignment, text wrap, material hierarchy, consistent shape containment, affordances, icon consistency and visual weight; no aesthetic score is a compliance certificate. Distinguish verified failures, suggestions and not tested. Severity reflects task impact, not a fixed community penalty score.

## V3 — performance evidence
Specify a user-visible task and metric before optimization (e.g., answer submit latency, sidebar resize jank, graph interaction, PDF page scroll). Capture baseline and candidate on identical workload, data, viewport, browser/device, cache and network state; separate cold/warm. Repeat representative runs, preserve raw samples and report distribution/variance (median and p95 only if sample size supports them), not a cherry-picked screenshot. Check long tasks, main-thread render/layout, network, memory growth, frame timing and cancellation/cleanup as relevant; use browser Performance API/DevTools/Playwright tracing for web, supported Instruments/xctrace for native. Distinguish code hypotheses from measured attribution; correlate request and commit IDs and label provider vs local work. Verify correctness before and after. Set budgets from actual baseline/product needs; no universal timing claims. If only static analysis, report no measured improvement.

## V4 — privacy-bounded telemetry
Define an event allowlist with typed schema, bounded low-cardinality fields and explicit purpose; unknown fields rejected or dropped, no raw prompts, answers, personal document contents, credentials or query strings in diagnostics. Use opaque correlation IDs without leaking identities, bounded buffering, retries, sampling, retention, access and deletion policy; lawful collection and opt-in where applicable. Test emitted events against allowlist, error/cancel/terminal events exactly once where contract requires, no unexpected network export, no private values in traces/logs. Separate local debug diagnostics from production telemetry; don't claim permission from a tool's availability. Prefer minimal existing instrumentation over new infrastructure.

## Delivery and test triage
Matrix: flow × state × viewport/input × expected behavior × evidence × actual result. Mark pass/fail/not-run/not-applicable with reason. Preserve trace artifacts only where privacy and rights permit. For failure reproduce smallest scenario, distinguish setup/infra from regression, fix and rerun targeted tests then relevant suite; never suppress failing assertions to get green. Capture both appearance and behavior; no deployment success without actual deployed result. For Exam App preserve question order, chosen answer, correct/incorrect distinction, technical retry, inspector and sidebar functionality; validate only requested stage scope.
