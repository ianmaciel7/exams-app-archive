# Pattern selection and validation

1. Classify the request: navigation, composition, editing, feedback, AI, data or visual styling. A pattern solves a recurring user problem; a style is an aesthetic vocabulary; an API is a mechanism, not a UX pattern.
2. Select by task, frequency, risk, screen size and input mode. Compare simpler alternatives before using richer effects or permanent panels.
3. Define normal, loading, empty, error, disabled, interruption, cancellation and success states. Preserve real backend state and user context.
4. Document trigger, origin/destination, duration, dwell, easing, interruption and reduced-motion behavior separately. Measure any real product motion before claiming exact timing.
5. Test keyboard, touch, screen reader, contrast, zoom, focus restoration, reduced motion, offline/error paths and slow devices. For drag add a non-drag alternative; for data interactions include explicit reset and accessible underlying data.
6. For AI use clear capability boundaries, review gates, cancellation, correction and honest evidence. Never equate generated confidence with factual reliability or visible activity with hidden reasoning.
7. Verify actual browser support, library version, dependencies and license. Track code commit, screenshot origin, capture date and exact media hash when saving media. Mark proposals and secondary research as such.
8. Validate with representative user tasks and metrics (time, error, success, recovery, preference). Do not claim trend popularity without comparable adoption data.

## Benchmark ingestion gate

Resolve each product source alias and observation ID centrally. Record typed product/feature/view/output/evidence relations only as supported. Distinguish official text, visual lead, observed UI and unverified candidate; validate references and rights. See [graph](ai-product-knowledge-graph.md).
